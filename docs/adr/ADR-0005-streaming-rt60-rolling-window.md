# ADR-0005: ストリーミングのRT60を、VAD遷移ではなくローリング窓の減衰イベント検出で測る

## ステータス

Accepted

## 日付

2026-09-22

## 関連

- issue #13（本ADRが扱う不具合）
- ADR-0003（現行のストリーミングRT60推定。「根本対策は観測窓の設計変更（別ADR）」と書き残している）
- ADR-0004（バッチ診断モード。ここで作った `find_decay_events` を再利用する）

## コンテキスト

ストリーミング経路のRT60推定は、**残響が強い部屋ほど測れなくなる**。残響を測るための機能が、残響が増えると先に壊れる。

原因は観測の起動条件にある。RT60の推定は `main.py:205` の

```python
if self._prev_speech and not speech_result.is_speech and self._prev_chunk is not None:
```

という発話→無音の遷移でしか起動しない。`SpeechDetector` は500msチャンク内の発話フレーム比率で `is_speech = speech_ratio > 0.3` を決めるため、残響の尾がノイズフロア+6dBを超えたままチャンクを埋めると `is_speech` が False に落ちず、遷移が発生しない。さらに遷移が起きても、`_extract_decay_segment` が見るのは直前の500msチャンクの末尾だけなので、RT60が長いほど減衰が窓に収まらない。

`tests/synth.py::reverberant_utterances`（真値既知、7秒、ADR-0003/0004 がRT60精度の検証に使っているハーネス）を500msチャンクで流した実測:

| 真値 RT60 | ポーズ | 発話→無音の遷移 | 減衰の切り出し | 採用 | 表示される値 | 信頼度 |
|---|---|---|---|---|---|---|
| 0.3 | 0.7s | 4 | 2 | 0 | 0.200 | 0.00 |
| 0.6 | 0.7s | 1 | 0 | 0 | 0.200 | 0.00 |
| 0.8 | 0.7s | **0** | 0 | 0 | 0.200 | 0.00 |
| 1.0 | 0.7s | **0** | 0 | 0 | 0.200 | 0.00 |
| 0.3 | 1.2s | 5 | 3 | 2 | **0.949** | 1.00 |
| 0.6 | 1.2s | 4 | 1 | 1 | **1.060** | 0.99 |
| 1.0 | 1.2s | 1 | 0 | 0 | 0.200 | 0.00 |

同じ信号をバッチ診断に通すと10条件すべてで真値±5%に収まる。**信号ではなく経路の問題である。**

加えて2つの表示上の問題がある。

- 採用イベントが1件でも、その値がそのまま `rt60` として、その1件のR²がそのまま信頼度として出る（真値0.6に対し1.060/信頼度0.99）。バッチ側は3件未満なら値を出さない。
- 推定が1件も無いときの `rt60` はフォールバックの **0.2** で、`dashboard/index.html:279` は信頼度を見ずに `rp.rt60.toFixed(2)` を描画する。**「測れていない」と「0.20秒の部屋」が画面で区別できない。**

## 検討した選択肢

### 論点1: 減衰区間の起動条件

#### 選択肢 1A: `SpeechDetector` の発話判定を変える（残響尾を無音側に倒す）

遷移が起きるようになるが、`is_speech` は SRMR の再計算ゲート（ADR-0002）・early-to-late ratio の孤立立ち上がり判定（ADR-0003）・原因分離の入力を兼ねている。RT60を測るために発話判定そのものを動かすと、独立検証済みの3経路すべての前提が同時に動く。**不採用。**

#### 選択肢 1B: ローリング窓に対して、バッチと同じ減衰イベント検出をかける（採用）

VADの遷移に依存せず、直近N秒のバッファを `find_decay_events`（ADR-0004）に通して減衰イベントを列挙し、ストリーミングと同じゲート（`is_valid` かつ R² ≥ `_RT60_CONFIDENCE_MIN`）を通ったものを集める。**起動条件が「発話が終わったこと」から「減衰が観測されたこと」に変わる。** 測りたいものが直接トリガになる。

イベントの重複採用は、イベント開始位置の絶対サンプル位置（10ms解像度）で除外する。窓の端で途切れているイベント（終端が窓末尾に達しているもの）は、減衰が完了していないので採用しない — 次のチャンクで窓に収まってから測る。

#### 選択肢 1C: `_extract_decay_segment` の窓だけ長くする

遷移が起きない条件（上表の RT60 0.8/1.0）では窓を伸ばしても起動しないので、問題の半分しか解けない。**不採用。**

### 論点2: ローリング窓の長さ

3秒の窓は**すでに存在する**。ADR-0002 で SRMR 用に第2リングバッファ（`SRMR_WINDOW_SAMPLES = 3 * SAMPLE_RATE`）を作り、`pipeline.process(chunk, srmr_window=...)` として毎チャンク渡している。新しいバッファを持たずに済む。

3秒で足りるかを実測した（10条件、シード1、集約は下記の決定と同じ pool=10 / p70）:

| 窓長 | 報告できた条件 | 最悪誤差 | 初回推定までの時間 | 1チャンクあたり |
|---|---|---|---|---|
| **3s（既存のSRMRバッファ）** | 10/10 | 8.5% | 3.0〜4.0s | 1.2〜1.4ms |
| 5s | 10/10 | 7.7% | 3.0〜4.5s | 1.7〜2.1ms |
| 7s | 10/10 | 6.4% | 3.0〜4.5s | 2.4〜2.6ms |

**3秒を採用する。** 窓を7秒に伸ばして得られるのは最悪誤差 8.5%→6.4% の改善だけで、そのために新しい7秒バッファ（224KB）と2倍の計算を持つ。1チャンクあたり1.3msは500msチャンクの0.26%であり、7秒窓の2.5msでも成立はするが、**既存バッファで足りるものを増やす理由がない。**

### 論点3: 集約

現行のストリーミングは `deque(maxlen=5)` の中央値、バッチは全イベントの70パーセンタイル（ADR-0004）。同じ10条件で実測した:

| プール上限 | パーセンタイル | 報告 | 最悪誤差 |
|---|---|---|---|
| 5 | 50（現行の集約） | 10/10 | 11.5% |
| 5 | 70 | 10/10 | 10.3% |
| **10** | **70** | **10/10** | **8.5%** |
| 10 | 50 | 10/10 | 11.0% |
| 無制限 | 70 | 10/10 | 8.5% |

**pool=10 / 70パーセンタイルを採用する。** 無制限と同じ精度が出るうえ、上限があるので部屋やマイクが変わったときに古い測定が残り続けない（7秒で採れるイベントは5〜10件なので、pool=10 はおおよそ「直近10秒ぶん」に相当する）。70が50に勝つ理由は ADR-0004 と同じ — 次の発話に尾を切られた減衰が下振れするため。シード1/2/3で最悪誤差 8.5 / 6.7 / 8.9%。

### 論点4: 「測れていない」をどう表すか

#### 選択肢 4A: `RoomProfile.rt60` を `float | None` にする

正確だが、`classify_room` / `CauseSeparator` / ダッシュボード / WSペイロードのすべてが None を扱う必要があり、独立検証済みの経路を広く触る。

#### 選択肢 4B: 採用イベント数の下限を設け、下回る間は `rt60_confidence = 0.0` とし、ダッシュボードは信頼度0のとき値を描かない（採用）

バッチと同じ「3件未満なら値を出さない」下限をストリーミングにも設ける。内部のフォールバック 0.2（`classify_room` の入力）は現状のまま残すが、**画面には出さない**。`rt60_confidence` はすでに `RoomProfile` にあり、WSペイロードにも乗っているので、型を変えずに「測れていない」を表現できる。

さらに、信頼度を「最後の1件のR²」から**「プール内のイベント数で頭打ちする値」**に変える。現行は1件でも0.99が出るため、値の少なさが信頼度に現れない。

## 決定

**1B（ローリング窓の減衰イベント検出）／窓長3秒（既存のSRMRバッファを再利用）／pool=10・70パーセンタイル／4B（3件未満は画面に出さない）を採用する。**

### 設計

1. 新モジュール `analysis/rolling_rt60.py` に `RollingRT60Estimator` を置く。`push(window: np.ndarray, window_start: int)` を毎チャンク呼び、内部で `find_decay_events`（`batch_diagnostic` から import）→ ゲート → `deque(maxlen=10)` に蓄積。`rt60` プロパティは3件未満なら `None`。
   - バッチのイベント検出ロジックは**再実装せず import する**。同じ規則が2箇所にあると、片方だけ直る。
   - 重複採用の除外はイベント開始の絶対サンプル位置（10ms解像度）で行う。窓末尾に達しているイベントは採用しない。
2. `AnalysisPipeline.process` は、`srmr_window` が渡されたとき（＝3秒バッファが埋まっているとき）に推定器へ渡す。`_prev_speech`/`_prev_chunk` による遷移検出と `_extract_decay_segment` は**削除する**。両方残すと同じ減衰が二重に採用される。
3. `RoomProfiler` は RT60 のプールを自分で持つのをやめ、推定器の結果を受け取る（`update_rt60(decay_segment)` → `set_rt60(value, confidence)`）。`_rt60_estimates` / `_last_rt60_confidence` は推定器側へ移る。
4. 信頼度は、3件に満たない間は 0、それ以降はプール内のR²の中央値とする。

   （当初この節は `min(1.0, len(pool) / MIN_RT60_EVENTS) * median(R²)` と書いていたが、**3件未満では `rt60` 自体が None を返す**ため第1項は報告時に常に1であり、式として意味を持たない。実装を式に合わせるのではなく、記述の方を実際の振る舞いに合わせた。現行は「1件でも0.99」だったのに対し、新実装は「3件揃うまで0」であり、**値の少なさが信頼度に現れる**という本来の意図は満たされている。）
5. `dashboard/index.html` は `rt60_confidence == 0` のとき RT60 を `--` と表示する。
6. early-to-late ratio の孤立立ち上がり検出（`_is_isolated_onset`）と SRMR ゲートは**変更しない**。本ADRはRT60の起動条件だけを対象とする。

## 検証方針

- **V1**: `reverberant_utterances` の10条件（真値 0.3/0.4/0.6/0.8/1.0 × ポーズ 0.7/1.2s）すべてで RT60 を報告し、誤差が±15%以内（ADR-0003 と同じ許容幅）。シード1/2/3で固定する。
- **V2**: 現行実装が遷移0回になる条件（真値0.8以上・ポーズ0.7s）で、新実装が報告できること。**これが本ADRの核心なので、退行したら即座に落ちるテストとして置く。**
- **V3**: 採用イベントが3件未満の間は `rt60_confidence == 0` であり、ダッシュボードが値を描かないこと。1件の推定がそのまま表示されないこと（issue #13 の後半）。
- **V4**: 同じ減衰イベントが二重に採用されないこと（窓が0.5秒ずつ進むので、同じイベントが最大6つの窓に現れる）。
- **V5**: 窓末尾で途切れているイベントを採用しないこと。
- **V6**: 連続発話（`apply_reverb(synth_speech(...))`、無音なし）では**値を出さない**こと。実測では採用0件で `None` になる。偽の部屋を作らないことを固定する。
- **V7**: 1チャンクあたりの処理時間が500msチャンクに対して十分小さいこと（実測1.2〜1.4ms）。`benchmarks/` に置く。

## 反証条件

次のいずれかが成り立てば、この決定は誤りである。

- V1 の10条件のうち1つでも報告できない、または誤差が±15%を超える
- 連続発話で偽のRT60が出る（V6）
- 1チャンクあたりの処理時間が現行比で10倍を超える

## 既知の限界（実測済み、本ADRでは解消しない）

- **発話内容そのものが持つ減衰の床**。`speech_utterances`（4Hz包絡の合成発話＋ポーズ）を残響ゼロで流すと、包絡の谷が減衰として採用され 0.202 が報告される（3件採用/10件棄却）。これはバッチ側と同じ値・同じ原因であり、ADR-0004 が `test_this_harness_cannot_measure_rt60` で固定した既知の限界。**小さい部屋のRT60がこの床に埋もれる可能性がある。** 本ADRは経路の欠陥（0件になる／1件を信頼して出す）を直すもので、この床は別の問題として残す。
- **長いRT60の過小評価**。真値1.0・ポーズ0.7sで −8.5%。次の発話が尾を切るためで、ADR-0004 が記録した入力側の限界と同じ。70パーセンタイルはこれを緩和するが消さない。
- **実マイクでの確認は未実施**。上記はすべて合成信号（-60dBFS床）である。

## レビュー結果

ユーザー指示により多観点レビューは省略（ADR-0004 と同じ運用）。実装前にユーザー承認を得た（2026-09-22）。
