# ADR-0004: 録音してから一括解析するバッチ診断モードを追加する

## ステータス

Accepted

## 日付

2026-09-18

## 関連ロードマップ項目

なし（ユーザー要望。参考: vaaaaanquish/MicrophoneTest）

## コンテキスト

acoustic-mirror は現状、500msチャンクごとのストリーミング解析しか持たない。用途は2つに分かれる。

- **マイク選び・セッティング調整**: 数秒話して、じっくり詳細な診断結果を見たい
- **発話中（通話中など）**: 継続的に今の状態を見たい（既存のリアルタイムダッシュボード）

前者にストリーミング解析は構造的に向いていない。ADR-0003 で記録したとおり、ストリーミングのRT60推定は
「発話→無音の遷移1回につき、直前の500msチャンク1個の残りから減衰1本」しか観測できない。
この観測窓（最大320〜470ms）の短さが、長いRT60の過小評価バイアスと、0.6s境界付近の誤分類の根本原因であり、
advisor レビューで3回バグを指摘された箇所でもある。ADR-0003 自身が「根本対策は観測窓の設計変更（別ADR）」と書き残している。

vaaaaanquish/MicrophoneTest は5〜7秒の録音全体から減衰イベントを多数拾い、その傾きの70パーセンタイルを採る。
単発推定の下振れ（残響尾のリップルが見かけ上速い減衰を作る）を集約で打ち消す方式であり、
「録音全体を先に持ってから解析する」バッチ文脈でこそ成立する。

### 前提として確定済みの判断（ユーザー確認済み）

1. **解析エンジン**: 既存の Python バックエンド（`SRMRProcessor` / `estimate_rt60_from_decay` / `estimate_early_to_late_ratio`）を再利用する。MicrophoneTest のようなクライアント側JS再実装はしない。
2. **指標の範囲**: MicrophoneTest の追加指標（SNR・クリッピング・周波数特性・ハム・ポップノイズ・総合MOSスコア等）は移植しない。既存3指標（SRMR・RT60・early-to-late ratio）の頑健性を「複数イベントのパーセンタイル集約」で上げることに限定する。
3. **録音場所**: ブラウザ（getUserMedia）で録音する。マイク比較が主用途なので、サーバー再起動（`--device`）なしでマイクを切り替えられることを優先する。
4. **UI**: 既存ダッシュボードとは別ページにする。

## 検討した選択肢

### 論点1: 録音データの受け渡し経路

#### 選択肢 1A: 既存 `DashboardServer` に `POST /api/diagnose` を追加する（WAVを送ってJSONが返る）

- メリット: 「録音1本を送って結果1個を受け取る」は要求/応答そのもので、HTTPの形に素直に合う。ブラウザ側は `fetch` 1回。既存の静的配信サーバーと同一オリジンなのでCORS不要。
- デメリット: 現行の `HTTPServer` はシングルスレッドで、解析中（数百ms〜1s程度）に静的ファイル配信が詰まる。→ `ThreadingHTTPServer` に替えれば解消（標準ライブラリ内の置き換えで済む）。

#### 選択肢 1B: 既存 WebSocket に `diagnose` メッセージ型を追加する

- メリット: 接続が1本で済む。
- デメリット: `WSBroadcaster` は全クライアントへの一方向ブロードキャスト専用で、クライアントからの受信は捨てている（`_handler`）。要求/応答の対応付け、送信元クライアントへの個別返信、バイナリフレーム処理を新たに作る必要があり、ブロードキャストという単一責務を崩す。

### 論点2: 複数イベント集約ロジックの置き場所

#### 選択肢 2A: 新モジュール `analysis/batch_diagnostic.py` に置く

- メリット: ストリーミング側の状態機械（`_rt60_estimates` deque・`_last_rt60_confidence`・ゲート付き `update_rt60`）と「クリップ全体を走査→N個集める→パーセンタイル」は形が違う。純関数 `diagnose(signal, sample_rate) -> DiagnosticResult` として分離すればテストしやすく、ストリーミング経路に一切触れない。
- デメリット: 閾値判定などで一部ロジックが `AnalysisPipeline` と似たものになる。→ 下位の推定関数（`estimate_rt60_from_decay` / `estimate_early_to_late_ratio` / `classify_room` / `SRMRProcessor` / `CauseSeparator`）は共有するので、重複はイベント検出部分だけに収まる。

#### 選択肢 2B: `RoomProfiler` に集約モードを足す

- デメリット: ストリーミング用の可変状態を持つクラスに、状態を持たない一括処理を同居させることになり、ADR-0003 で3回バグが出た箇所の複雑性をさらに上げる。不採用。

## 決定

**1A（HTTP `POST /api/diagnose`）と 2A（新モジュール）を採用する。**

**理由**: どちらも「既存のストリーミング経路を一切変えない」ことを優先した。ストリーミング側は独立検証済み（153テスト）であり、バッチモード追加のためにそこを触る理由がない。

### 設計

**ブラウザ側（新規 `dashboard/diagnose.html`）**:
1. `navigator.mediaDevices.enumerateDevices()` でマイク一覧をドロップダウン表示する。
2. getUserMedia の制約で `echoCancellation: false` / `noiseSuppression: false` / `autoGainControl: false` を**常に**指定する。ブラウザの信号処理が入ると、測りたい部屋の残響・マイク特性そのものが加工されてしまい、測定の前提が崩れるため（MicrophoneTest はトグル式だが、本プロジェクトは測定器寄りなので固定でOFFにする）。
3. AudioWorklet で Float32 PCM を集める。MediaRecorder は使わない（Opus等の非可逆圧縮が残響尾・変調スペクトルを変質させるため）。
4. 既定7秒録音（カウントダウン表示付き）。16-bit PCM モノラル WAV にエンコードし、**ブラウザのネイティブサンプルレートのまま**送る。リサンプリングはサーバー側に寄せる（JSでアンチエイリアス付きリサンプラを書くより `scipy.signal.resample_poly` の方が正しさを保証しやすい）。
5. 結果表示: SRMR・了解度比・部屋種別・RT60（採用イベント数とばらつき付き）・early-to-late ratio・ノイズフロア・原因診断。既存 `index.html` からリンクを1本張る。

**サーバー側**:
1. `DashboardServer` を `ThreadingHTTPServer` に替え、`DashboardHandler.do_POST` で `/api/diagnose` を処理する。
   - 本文を標準ライブラリ `wave` で読む。モノラル・16-bit 以外は 400。
   - 長さ制限: 3秒未満（SRMR窓 = `SRMR_WINDOW_SAMPLES`）は 400、30秒超（またはそれ相当の `Content-Length`）は 413。バインドは既存どおり `localhost`。
   - 解析例外は 500 + JSON エラー。成功時は 200 + `DiagnosticResult.to_dict()`。
2. `analysis/batch_diagnostic.py` の `diagnose(signal, sample_rate)`:
   1. 16kHz 以外なら `resample_poly` で 16kHz に変換する（既存解析はすべて16kHz前提）。
   2. **フレームエネルギーとノイズフロアを録音全体から一括算出する**。ストリーミングの `SpeechDetector` は適応的ノイズフロアを持つ状態付きクラスで、録音冒頭では収束していないため流用しない。フレームサイズは `SpeechDetector` と同じ30ms、ノイズフロアはフレームエネルギーの低位パーセンタイル（初期値10%）、発話閾値は `SpeechDetector` と同じマージンを使う。
   3. **RT60**: 発話→無音の遷移をすべて列挙し、各遷移から次の発話開始（または上限1s）までを減衰区間として `estimate_rt60_from_decay` にかける。ストリーミングと同じゲート（`is_valid` かつ R² ≥ `_RT60_CONFIDENCE_MIN`）を通った推定だけを集め、**パーセンタイルで集約する（初期値70%、MicrophoneTest準拠）**。採用イベントが3件未満なら RT60 は「判定不能」とし、値を出さない（ADR-0003 の「不正確な値を出すより出さない」方針を継承）。
      - ストリーミングとの本質的な違いは減衰区間の長さ。500msチャンクの残りではなく、次の発話までの無音全体（最大1s）を使えるため、T20 の -25dB まで届くイベントが増え、ADR-0003 に記録した長いRT60の過小評価が縮むことが期待できる。
   4. **Early-to-late ratio**: 孤立立ち上がり（直前200msが無音、ADR-0003 と同じ条件）をすべて列挙して `estimate_early_to_late_ratio` を適用し、中央値で集約する。0件なら判定不能。
   5. **SRMR**: 発話フレームの比率が `_SRMR_GATE_MIN_SPEECH_RATIO` を満たす場合に限り、録音全体に対して `SRMRProcessor` を1回かける。
   6. `classify_room` → `srmr_target` → `CauseSeparator.diagnose` は既存関数をそのまま呼ぶ。判定不能の指標がある場合は、ストリーミングと同じ既定値で分類し、結果に「推定値を使っていない」ことを明示するフラグを付ける。
   7. 返り値 `DiagnosticResult` には集約値に加え、採用・棄却イベント数と採用された個々のRT60値を含める。「何本の減衰から出た数字か」を見せることが、バッチモードの存在理由そのものなので。

### 検証方針（反証条件）

本ADRの中心仮説は「**複数イベントのパーセンタイル集約は、ストリーミングの単発推定より RT60 を正確に出す**」である。

- 既存の合成RIRハーネス（`tests/synth.py` の `apply_reverb`）で、真値 RT60 = 0.3 / 0.6 / 1.0 / 1.5s の残響付き合成音声（7秒）を作り、`diagnose` の RT60 誤差を測る。
- 合格基準（初期値）: 各真値で相対誤差 ±15% 以内。かつ ADR-0003 で過小評価21%を記録した 1.5s ケースで、ストリーミングより誤差が小さい。
- **反証条件**: 同じ入力に対してパーセンタイル集約の誤差がストリーミング単発推定の誤差と同等以上なら、仮説は棄却とし、70% という値またはイベント抽出方法を見直す（あるいはバッチモードで RT60 を出すこと自体を再検討する）。
- パーセンタイル値70%は MicrophoneTest の推定器（ピーク-3〜-25dBの生エネルギー傾き）向けの値であり、Schroeder+T20 の本推定器にそのまま最適とは限らない。上記ハーネスで50/70%を比較し、根拠のある値を選ぶ。

## 影響

- `DashboardServer` の基底が `HTTPServer` → `ThreadingHTTPServer` に変わる。静的配信の挙動は変わらないが、既存 `tests/test_dashboard.py` の再確認が必要。
- 新規ファイル: `analysis/batch_diagnostic.py`、`dashboard/diagnose.html`、対応テスト。`index.html` にはリンク1本のみ追加。
- ストリーミング経路（`AnalysisPipeline` / `RoomProfiler` / `WSBroadcaster` / `capture.py`）は変更しない。
- バッチ診断中もサーバー側の `sounddevice` ストリームは動き続ける。同一マイクを2箇所から開くことになるが、macOS の CoreAudio では共有可能で実害はない想定。問題が出たら別途扱う。
- ブラウザの `getUserMedia` は `localhost` なら HTTPS 不要（secure context 扱い）。既存の `localhost` バインドのままで動く。
- マイク切り替えで**ブラウザ経由とサーバー（sounddevice）経由の入力経路が別物になる**。同じマイクでも、リアルタイムダッシュボードとバッチ診断の数値が完全には一致しない可能性がある（OSレベルの入力処理の差）。許容リスクとし、README に明記する。
- **総合スコア（MOS等）は出さない。** MicrophoneTest の `rToMos()` は ITU-T G.107 の R→MOS 変換式をアドホックな加重スコアに流用しており、ADR-0001 で是正したのと同種の誤り（文献の出力曲線を、その入力ではない値に当てはめる）である。スコープを広げて総合スコアを入れる場合も、この式は流用しない。
