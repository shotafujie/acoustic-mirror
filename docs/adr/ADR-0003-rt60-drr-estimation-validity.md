# ADR-0003: RT60/DRR推定を前提の成立する条件に限定して是正する

## ステータス

Accepted

## 日付

2026-09-16

## 関連ロードマップ項目

なし（Issue起票 #9 に基づく是正）

## コンテキスト

`RoomProfiler`（`analysis/room_profiler.py`）のRT60/DRR推定が、前提の成立しない条件で計算されている。

**RT60**: `_extract_decay_segment`（main.py）は最短50msの減衰区間を受け付ける。`estimate_rt60_from_decay` はピークから-30dB以内の範囲で線形回帰し60dB減衰を外挿するが、50msという短い観測から60dB減衰を外挿するのは統計的に無理があり、実際には発話終了直後にノイズフロアへ到達した区間の傾きを測っている可能性が高い（ノイズフロアが-40dB程度なら回帰区間の大半がフロアになる）。

**DRR**: `estimate_drr` はオンセットから0-50msを直接音、50-200msを残響としている。連続発話では50-200msの区間に次の音素の直接音が含まれるため、インパルス応答に対するDRRの定義とは別物であり、話速に強く依存する。

`RoomProfile.rt60` / `drr_db` は `classify_room` と `CauseSeparator` の両方に入力される。ここが不正確だと部屋分類→SRMR目標値（ADR-0001）→原因診断がすべてずれる。

## 検討した選択肢

### 選択肢 A: RT60はSchroeder積分+T20回帰+最低減衰長300ms、DRRは名称変更+孤立立ち上がり限定

- 概要: RT60はエネルギーを末尾から累積するSchroeder積分に置き換え、回帰区間をノイズフロアの影響を受けにくいT20（-5dB〜-25dB）に限定し、最低減衰長を300msに引き上げる。DRRは「オンセット早期/後期エネルギー比」という近似指標であることが分かる名前に変更し、直前が無音だったオンセットのみを更新対象にする。
- メリット: 既存アーキテクチャ（発話境界イベント駆動の推定、`RoomProfiler`の状態管理）を保ったまま、信号処理としての前提の誤りだけを修正できる。段階的な変更で済み、他モジュールへの影響が小さい。
- デメリット: T20回帰やSchroeder積分を実装する分のコストが増える。DRRの孤立立ち上がりゲートにより、連続発話中の更新頻度が下がる。

### 選択肢 B: RT60/DRRの推定自体をやめ、固定値または外部キャリブレーション入力に置き換える

- 概要: ブラインド推定をやめ、ユーザーが部屋の種類を手動選択する、または初回起動時のキャリブレーション手順（無音区間での測定など）に置き換える。
- メリット: 信号処理としての前提違反を精度ゼロで回避できる。実装がシンプル。
- デメリット: `RoomProfiler` の目的（測定機材なしでのブラインド推定）を放棄することになり、プロダクトとしての価値（環境が変わるたびに手動設定が要る）が下がる。今回のIssueは「推定精度の是正」であり「推定機能の削除」ではないため、要求されている解決の範囲を超える。

### 選択肢 C: 現状維持（何もしない）

- 概要: 何も変更しない。
- メリット: コストゼロ。
- デメリット: ノイズフロアの傾きをRT60として誤推定し続け、部屋分類・SRMR目標値・原因診断のすべてがこの誤差の上に乗る。

## 決定

選択肢 A を採用する。

**理由**: Bは問題を機能ごと消すだけで、ブラインド推定というプロダクトの前提を壊す。Aは信号処理の前提違反という原因に直接対処し、既存の呼び出し構造（main.pyの発話境界イベント検出→RoomProfiler更新）を変えずに済む。

### 設計

**RT60**:
1. `estimate_rt60_from_decay` の内部処理をSchroeder積分に置き換える。**Schroeder積分は生波形サンプルにではなく、既存の10msフレームエネルギー配列（`energies`, 300ms観測なら30点程度の小配列）に対して適用する**（`np.cumsum(energies[::-1])[::-1]`）。生波形（sample_rate×300ms=4800サンプル）に対して逆順コピー・二乗・累積和を行うのはリアルタイムループの発話終了イベントごとに不要なアロケーションを生むため避ける（レビュー指摘への対応）。
2. 回帰区間をピークから-30dBではなくT20（-5dB〜-25dB）に限定し、60dB相当に外挿する。T20区間が確保できない場合はT10などへのフォールバックはせず、`is_valid=False` として推定をスキップする（理由は下記「未決事項への回答」を参照）。
3. `_extract_decay_segment`（main.py）の最低減衰長を `sample_rate * 0.05`（50ms）から `sample_rate * 0.3`（300ms）に引き上げる。
4. 信頼度は `scipy.stats.linregress` が返す `rvalue` を再利用し `rvalue ** 2`（R²）とする。**別途R²を計算する処理は追加しない**（レビュー指摘への対応: 二重計算の防止）。
5. **戻り値の型変更を`RoomProfiler`内部に閉じ込める**: `estimate_rt60_from_decay` は `RT60Estimate(rt60: float, confidence: float, is_valid: bool)` という小さなdataclassを返すが、これを呼び出すのは `RoomProfiler.update_rt60` のみである。`RoomProfiler._rt60_estimates`（中央値計算用のdeque）の型は変更せず `deque[float]` のままとし、R²が閾値未満（提案: 0.5）または`is_valid=False`の推定はそもそも`_rt60_estimates`に追加しない。信頼度は集約せず、**`RoomProfiler`に`_last_rt60_confidence: float`という単一スカラーを新設し、直近の「採用された（=deque追加された）」推定の信頼度で上書きする**方式にする（レビュー指摘への対応: 集約規則を「最新の採用済み推定の値をそのまま使う」に確定し、`_rt60_estimates`自体の型変更は避ける）。

**DRR**:
1. `estimate_drr` を `estimate_early_to_late_ratio` にリネームし、docstringで「インパルス応答に対するDRRの定義とは別物の近似指標」と明記する。**`RoomProfile.drr_db` フィールドも `early_to_late_ratio_db` にリネームする**（レビュー指摘への対応: 関数名だけ変えてフィールド名を`drr_db`のまま残すと、to_dict()やCauseSeparatorの消費側でDRRの定義誤解が温存される）。
2. オンセット検出時、直前200ms（`SpeechDetector`のフレームサイズ30ms×約7フレーム相当）が無音（ノイズフロア+閾値以下）だった場合のみ更新対象にする「孤立立ち上がりゲート」を追加する。**この無音判定は`main.py`側（`AnalysisPipeline`）が持つ**: `AnalysisPipeline`は既に`speech_result.frame_energies`と`_prev_speech`を保持しており、オンセット直前200msが無音だったかはこの既存状態から判定できるため、`RoomProfiler`に新たな時系列状態を持たせる必要はない（レビュー指摘への対応: 判定主体の明確化）。連続発話中の大半のオンセットはこのゲートで除外されるが、`RoomProfiler._early_to_late_ratio_db` はもともと直近の推定値を保持し続けるだけの状態であり、更新頻度が下がっても最後の信頼できる値を保持し続ければ実害は小さい。

**信頼度の伝搬**:
`RoomProfile` に `rt60_confidence: float`（`RoomProfiler._last_rt60_confidence`の値）を追加する。`CauseSeparator` 側でこれを消費するロジック（低信頼時にreverb診断の重みを下げる等）は、原因不明状態の設計を扱うIssue #7のADRに委ねる。本ADRの責務は `RoomProfile` に信頼度フィールドを追加するところまでとする。

### 未決事項への回答

- **R²閾値（提案: 0.5）**: 「低信頼」判定の初期値として0.5を採用する。R²=0.5は回帰直線が分散の半分しか説明できていない状態であり、減衰カーブとしての線形性が怪しいラインとして妥当。実測で外れれば調整する。
- **静かな環境でT20区間に届く前にノイズフロアに到達するケース**: T10などへのフォールバックは追加せず、`is_valid=False` として推定をスキップする。理由: 緩い区間へのフォールバックは「精度の低い推定を承知で出す」方向であり、ADR-0001で採る「不正確な値を出すより出さない方がよい」という考え方と矛盾する。まず出さない選択をし、実運用でサンプル不足（`_rt60_estimates` が常に空に近い）が問題になったら再検討する。
- **DRR孤立立ち上がりの無音長閾値（提案: 200ms）**: 初期値として採用する。`SpeechDetector` のフレームサイズ（30ms）の約7フレーム分で、短いブレスポーズと発話の切れ目を区別できる長さとして妥当と判断した。実測で調整する。

## 影響

- `estimate_drr` → `estimate_early_to_late_ratio` へのリネームに加え、`RoomProfile.drr_db` → `early_to_late_ratio_db` へのフィールド名変更も行う。呼び出し元（main.py）・既存テスト・`to_dict()`の出力キーへの破壊的変更。
- `estimate_rt60_from_decay` の戻り値変更（float → `RT60Estimate` dataclass）は `RoomProfiler.update_rt60` の内部だけに閉じ込め、`RoomProfiler._rt60_estimates`（deque）の型は変更しない。呼び出し元とテストへの影響は `estimate_rt60_from_decay` を直接呼んでいるテストのみに限定される。
- `RoomProfile` に `rt60_confidence` フィールドが増えるため、`to_dict()`（main.py の `AnalysisResult.to_dict()`）やテストフィクスチャに影響する。
- RT60推定が「出さない」ケースが増えるため、起動直後や環境ノイズが大きい場面で `RoomProfiler._rt60_estimates` が空のまま続く期間が伸びる可能性がある。これは許容するリスクとして受け入れる（デフォルト値0.2sのまま部屋分類が続くが、誤った低RT60推定よりは安全側）。
- DRR（early-to-late ratio）更新頻度が下がることで、`RoomProfile.early_to_late_ratio_db` が古い値のまま長く保持される可能性がある。これも許容するリスクとして受け入れる。
- 孤立立ち上がりゲートの無音判定を`AnalysisPipeline`側に持たせることで、`main.py`のオンセット検出処理（main.py:141-150）に条件分岐が1つ増える。

## レビュー結果

`性能` `複雑性` `データモデル` の3観点でレビューを実施。

| 指摘 | 重要度 | 対応 |
|---|---|---|
| Schroeder積分を生波形に適用すると誤読される記述だった | Major（性能） | 決定を変更: フレームエネルギー配列に適用すると明記 |
| R²の二重計算リスク | Minor（性能） | 決定を変更: `linregress`の`rvalue**2`を再利用すると明記 |
| 戻り値型変更（float→dataclass）の波及範囲が未定義 | Major（複雑性） | 決定を変更: 型変更を`RoomProfiler.update_rt60`内部に閉じ込め、`_rt60_estimates`の型は維持 |
| 孤立立ち上がりゲートの無音判定主体が未定義 | Minor（複雑性） | 決定を変更: `AnalysisPipeline`（main.py）側が持つと明記 |
| rt60_confidenceの集約規則が未定義 | Blocker（データモデル） | 決定を変更: 「最新の採用済み推定の値をそのまま使う」方式に確定 |
| `drr_db`フィールド名が関数リネームと不整合 | Major（データモデル） | 決定を変更: `early_to_late_ratio_db`にリネーム |

Blocker 1件・Major 3件・Minor 2件はすべて決定・影響への反映で解消。未決着の指摘なし。
