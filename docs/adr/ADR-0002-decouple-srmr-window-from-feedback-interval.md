# ADR-0002: SRMR解析窓をVAD/フィードバック更新間隔から分離する

## ステータス

Accepted

## 日付

2026-09-16

## 関連ロードマップ項目

なし（Issue起票 #2 に基づく是正）

## コンテキスト

`CHUNK_SAMPLES = 8000`（500ms, `main.py`）を解析窓としてSRMRを計算している。`compute_modulation_energy` は包絡を400Hzに間引くため、500msの窓では包絡が200点、FFT分解能は2Hzになる。各変調帯域に入るビン数を数えると、低変調帯域（4.0Hz, 6.3Hz）はそれぞれ1ビンしかなく、SRMRの分子（低変調4帯域の合計9ビン）がほぼ単一のFFTビンの値で決まっている。

SRMRは原著（Falk et al. 2010）でも数秒の発話全体を単位とする指標であり、500msという窓長はこの指標の前提を満たしていない。

一方で、`AnalysisPipeline` は同じ500msチャンクをVAD（`SpeechDetector`）、RT60推定（`_extract_decay_segment`）、DRR推定（オンセット検出）にも使っており、これらは発話の立ち上がり・立ち下がりを500ms単位で検出することを前提にしている。触覚フィードバックの即時性も、この応答性に依存している。

## 検討した選択肢

### 選択肢 A: 全体のチャンク長を3秒に伸ばす（単一バッファ）

- 概要: `CHUNK_SAMPLES` を 48000（3秒）に変更し、VAD・RT60・DRR・SRMRすべてを同じ3秒窓で計算する。
- メリット: `RingBuffer` は窓長に依存しない実装（常に最新N samplesを返す）なので、定数を1つ変えるだけで済む。実装コストが最小。
- デメリット: `_extract_decay_segment`（main.py）は「1チャンクに1回の発話終端を検出する」ロジックであり、3秒窓には複数の発話境界が入りうるため、RT60推定が同一の減衰イベントを重複検出したり、境界を誤検出したりする。`is_speech`（`speech_ratio > 0.3` を3秒窓全体で評価）の反応が鈍り、リアルタイム性が要求される触覚フィードバックの即時性が損なわれる。

### 選択肢 B: VAD用の500msバッファとSRMR用の3秒バッファを分離する

- 概要: 既存の500ms `RingBuffer` はそのまま残し、SRMR専用に3秒の`RingBuffer`を追加する。500msの主ループでVAD/RT60/DRRを今まで通り実行しつつ、直近の発話継続状況を見てSRMR用バッファが「発話で埋まっている」と判断できたときだけSRMRを計算する。
- メリット: `RingBuffer` 自体は無改造で流用できる。既存のVAD/RT60/DRRロジック・触覚フィードバックの即時性に影響を与えない。SRMR側だけを原著の前提（数秒の発話単位）に合わせられる。
- デメリット: 音声コールバックが複数バッファに書き込む必要があり、`capture.py` の `open_stream()` のシグネチャ変更が要る。SRMR計算のゲート条件（どの程度発話が続いていれば計算するか）を新たに設計・チューニングする必要がある。

### 選択肢 C: 現状維持（何もしない）

- 概要: 500ms窓のまま。
- メリット: コストゼロ。
- デメリット: SRMRの分子がほぼ単一FFTビンで決まる状態が続き、指標としての信頼性が低いまま。#1の閾値是正を行っても、窓長由来の分散の大きさは解消されない。

## 決定

選択肢 B を採用する。

**理由**: 選択肢Aは実装コストが最小だが、既存のVAD/RT60/DRRロジックが暗黙に前提としている「チャンク＝短い応答単位」という設計と衝突し、`_extract_decay_segment` の重複検出やフィードバック遅延という新たな不具合を生む。Bはコストは高いが、責務ごとに要求される時間スケールが異なるという実態（VAD/RT60/DRRは応答性、SRMRは統計的安定性）にアーキテクチャを合わせる方針であり、副作用を局所化できる。

### 設計

1. `SRMR_WINDOW_SAMPLES = 3 * SAMPLE_RATE`（3秒）で2本目の `RingBuffer` を追加する。
2. `open_stream()` のコールバックは `buffers: Sequence[RingBuffer]` のような無名の集合ではなく、**`vad_buffer: RingBuffer, srmr_buffer: RingBuffer` という明示引数**を取るよう変更する（レビュー指摘: 型で用途が区別できないと将来のバッファ追加時に意図が読み取れなくなる）。
3. `AnalysisPipeline` に直近の `is_speech` 履歴を `deque(maxlen=6)`（500ms×6=3秒相当）で保持する。
4. SRMR計算のゲート判定は、状態（`is_speech`履歴のdeque・前回計算時刻）を持たない**純粋関数** `should_recompute_srmr(recent_speech_ratio: float, seconds_since_last_compute: float, buffer_full: bool) -> bool` として実装する（レビュー指摘: 「70%閾値」と「1秒間引き」の2つの独立した状態のANDで挙動が決まると、チューニング時に内部状態を両方追わないと予測できず認知コストが上がる。ロジックを状態から切り離すことで、テストも純粋関数への入力パターンとして書ける）。判定条件そのものは変更しない: `buffer_full` かつ直近履歴の **70%以上** が `is_speech=True` かつ `seconds_since_last_compute >= 1.0` のときだけ `srmr_buf.get_window()`（最新3秒、500msごとにスライドするオーバーラップ窓）を `SRMRProcessor` に渡す。不成立なら `SRMRResult(is_valid=False)` を返す。
5. 既存の「非speechフレームは前回スコアを持ち越す」ロジック（main.py:167-172）を拡張し、**持ち越したスコアが何秒前に計算されたものかを示す `age_seconds` を `AnalysisResult` に追加する**（レビュー指摘: ゲート不成立時の持ち越し期間が現状の数百msから秒〜数十秒に伸びるため、`is_valid`の2値だけでは「新鮮なスコアか数十秒前のスコアか」が下流から区別できない）。下流（ダッシュボード）での`age_seconds`の具体的な使い方（警告表示の閾値等）は本ADRのスコープ外とし、フィールド追加のみを担当する。
6. 500msの主ループ・VAD/RT60/DRRロジックは変更しない。ただしSRMR計算自体は`AnalysisPipeline.process()`と同期実行のままであるため、3秒窓のgammatone+Hilbert+FFTがメインループの1イテレーションを遅延させる（下記「性能への影響」を参照）。

### 未決事項への回答

- **ゲート閾値（70%）と履歴長（6ティック=3秒）**: 初期値としてこれを採用する。3秒バッファのほぼ全域が発話であることを求めるのは自然発話中の短いポーズ（数百ms）を弾きすぎる一方、50%以下では無音混入が支配的になりSRMRの意味が薄れる。70%は「3秒中2.1秒以上が発話」というラインで、通常のポーズを許容しつつ発話区間らしさを担保する妥協点として採用する。実測（#10のテストと合わせて）で外れればチューニングする。
- **ヒステリシス**: 今回は入れない。ゲートのON/OFF頻度が実機検証で問題になったら追加を検討する（YAGNI）。
- **CPU負荷**: 「前回計算から1秒以上」の間引きを設計に含めることで対応する。実機計測してなお問題があれば、間引き間隔をさらに伸ばす。
- **無音混入の扱い**: 3秒窓に含まれる無音はそのままSRMR計算にかけ、フレーム単位での音声区間抜き出し・連結は行わない。SRMR原論文も自然発話中の短いポーズを許容する前提であり、フレーム抜き出しはこの是正の範囲を超える過剰実装になる。ゲート（70%閾値）で「無音が支配的な窓」は既に除外される。

## 影響

- `capture.py` の `open_stream()` のシグネチャ変更は破壊的変更。呼び出し元（`main.py`）を合わせて変更する。
- SRMR結果の更新頻度が実質的に「直近3秒のうち70%以上が発話」という条件に依存するようになり、連続発話中でも1秒間隔でしか動かなくなる。ダッシュボードの表示が従来より緩やかに更新される見え方になる点をREADME等に記載する。
- **性能への影響（実装前に計測する）**: SRMR計算は`AnalysisPipeline.process()`と同一スレッド・同期実行のため、3秒窓のgammatoneフィルタ適用の実処理時間が、そのままメインループの1イテレーションに加算される。実測コストの主因は`hilbert`のFFT長ではなく`_apply_fir`が23チャンネルを`np.convolve(mode="full")`でループする実装（3秒窓では1チャンネルあたり約48000×129回、23チャンネルで約1.4億回積和）である（**訂正**: 48000=2⁷×3×5³は5-smoothでnumpyのFFTが素直に扱える長さであり、「2の冪でないためFFTが遅い」という当初の懸念は誤りだったため撤回する。ゼロパディング対策は不要）。実装時に以下を行う:
  - `SRMRProcessor.process()`に3秒窓を渡した場合の実測所要時間を計測する。
  - 500msの主ループ周期を明確に超える（目安: 100ms以上）場合は、まず`_apply_fir`（`GammatoneFilterbank.apply`）を`scipy.signal.fftconvolve(signal, bank, axes=1)`でチャンネル一括処理するよう置き換える（23回のPythonループ+convolveをやめ、フィルタバンク全体を1回のFFT畳み込みにまとめる）。これで解決しない場合に初めて、SRMR計算を別スレッド/別プロセスに逃がす非同期化を次の是正候補として別ADRで検討する。
  - 追加バッファのメモリ増分（float32で48000サンプル≒188KB程度）は無視できる規模であり、対応不要と判断する。
  - **実測結果（実装時）**: `SRMRProcessor.process()`に3秒窓（#4/#5適用後）を20回渡して平均したところ、1回あたり約41.6ms。500msの主ループ予算・目安の100ms閾値の両方に十分収まっており、`fftconvolve`への置き換えや非同期化は現時点では不要と判断した。負荷が高い環境（低スペック機）での再計測は将来の課題として残す。
- 許容するリスク: ゲート閾値・履歴長・間引き間隔は実測前の初期値であり、実運用でチューニングが必要になる可能性がある。SRMR計算が同期実行のままである間、3秒窓の処理時間次第ではメインループの応答性がティックごとに揺らぐリスクを許容する（計測してから非同期化を判断する）。

## レビュー結果

`性能` `複雑性` `データモデル` の3観点でレビューを実施。

| 指摘 | 重要度 | 対応 |
|---|---|---|
| 3秒窓のgammatone+Hilbert+FFTコスト見積りが粗く、同期実行がメインループを遅延させる可能性が未検討 | Major（性能） | 決定を変更: 影響節に実測手順と非同期化への移行条件を明記 |
| 選択肢A/Bのメモリ増分が数値比較されていない | Minor（性能） | 決定を変更: 増分は無視できる規模と明記して対応不要と判断 |
| 「70%閾値」と「1秒間引き」の二重ゲート状態が認知コストを上げる | Major（複雑性） | 決定を変更: ゲート判定を状態を持たない純粋関数として分離 |
| `Sequence[RingBuffer]`では用途が型で区別できない | Minor（複雑性） | 決定を変更: 明示引数（`vad_buffer`, `srmr_buffer`）に変更 |
| 持ち越しスコアにstaleness情報がなく、is_valid の2値では鮮度が区別できない | Major（データモデル） | 決定を変更: `AnalysisResult`に`age_seconds`を追加 |
| ゲート境界のバタつきが記録されない | Minor（データモデル） | 受け入れる: ヒステリシス未導入はADRの既定方針どおり。実測で問題化したら追加 |

Blockerなし。Major 4件・Minor 2件のうち5件は決定・影響への反映で解消、1件（バタつき）はリスクとして明示的に受け入れる。
