# ADR-0001: SRMR実装をSRMRpy準拠の方向に寄せ、閾値は実測で引き直す

## ステータス

Accepted

## 日付

2026-09-16

## 関連ロードマップ項目

なし（Issue起票 #1, #4, #5, #6 に基づく是正）

## コンテキスト

`analysis/srmr.py` の SRMR 実装は独自実装で、文献の閾値（`RoomType.srmr_target` に置かれている 2.0〜5.0 の値）をそのまま使っている。しかし合成音声（3秒・4Hz変調、指数減衰ノイズRIRを畳み込み）で参照実装 SRMRpy と比較すると、一貫して 1/3 程度の値になる。

| RT60 | acoustic-mirror | SRMRpy |
|---|---|---|
| Dry | 2.43 | 6.26 |
| 0.16s | 3.55 | 12.46 |
| 0.36s | 2.58 | 7.64 |
| 0.61s | 1.37 | 4.56 |
| 1.0s | 0.99 | 3.18 |

QUIET_SMALL の目標値 5.0 は自実装では乾いた音声でも到達せず、`intelligibility_ratio` が常時0.5を下回り `overall` が恒常的に `alert` になっている。

差分を調べたところ、値のズレには実装上のバグが混ざっている。

- **#4**: 包絡のダウンサンプリング（`env[::downsample_factor]`）にアンチエイリアスフィルタがなく、高域チャンネル（cf=7500Hz）で包絡の200Hz超成分の24.8%が折り返す。`scipy.signal.decimate` に置き換えると SRMR が 2.43→2.82（1割以上）変化した。
- **#5**: 変調スペクトルのFFT前に窓関数がなく（DC除去のみ）、低変調帯域のエネルギーが高変調帯域（分母）に漏れる。SRMRを系統的に低く見積もる方向に働く。
- **#6**: 原法（Falk et al. 2010）との差分（K\*固定・変調帯域上限が docstring と実装で100Hz/128Hzに食い違う）がコード上に明記されていない。「Reference: Falk et al. (2010)」という表記から原著準拠だと誤解される。

これら3件は「SRMR値のスケールが何によって決まるべきか」という一つの決定に従属する。#4/#5を直せばSRMR値そのものが変わるため、閾値（#1）をどこに置くかは#4/#5を直した後でないと決められない。

## 検討した選択肢

### 選択肢 A: 自実装のまま、実測分布に合わせて閾値を引き直す

- 概要: #4/#5のバグ修正はせず、現在の実装が出す値の分布を実測し、`_SRMR_TARGETS` をそのスケールに合わせて再設定する。
- メリット: 実装変更が閾値の1ファイルに閉じる。着手コストが最小。
- デメリット: アンチエイリアス欠如・窓関数欠如という実装バグを放置したまま閾値だけ合わせることになる。将来的にバグを直した時（直さない理由がない）、また閾値がズレて同じ問題が再発する。文献の目安値（SRMRpy等）と一切対応しない独自スケールになり、外部の知見（既存研究のSRMR-明瞭度対応表など）を参照できなくなる。

### 選択肢 B: SRMRpy準拠に実装を寄せ、文献値をそのまま閾値に使う

- 概要: #4（アンチエイリアス）・#5（窓関数）を原法に忠実な実装に直し、K\*固定や矩形帯域分割などの残る簡略化はdocstringに明記して受け入れる。閾値は#4/#5修正後に合成音声で実測して決め直す。
- メリット: 既知のバグ（アンチエイリアスなし、窓関数なし）はどのみち直すべきものであり、"バグを直す"と"参照実装に近づく"が同じ作業で両立する。文献の目安値（SRMRpy、既存研究のSRMR-明瞭度対応）を閾値決定の参考にできる。
- デメリット: 完全準拠（K\*の適応的決定、Q=2の真の変調フィルタバンク）までは踏み込まないため、SRMRpyとの値は依然として一致しない。「準拠」の範囲を明記しないと将来また誤解を生む。

### 選択肢 C: 現状維持（何もしない）

- 概要: 何も変更しない。
- メリット: コストゼロ。
- デメリット: `overall` が恒常的に `alert` になる既知の不具合を放置する。ユーザー向けプロダクトとして許容できない。

## 決定

選択肢 B を採用する。ただし完全準拠（K\*の適応決定、真の変調フィルタバンク設計）までは今回のスコープに含めない。

**理由**: #4/#5は信号処理として明確な誤り（エイリアシング、スペクトル漏れ）であり、直す方向に選択の余地がない。これを直すことは同時に参照実装との差を縮める効果があるため、"バグ修正"と"閾値の妥当性回復"を一つの作業に統合できる。完全準拠まで手を広げると適応的K\*決定や真の変調フィルタバンク設計という別種の実装コストが発生し、今回のバグ修正の範囲を超えるため見送る。閾値の具体的な数値は、#4/#5修正後でなければ決め打ちできないため、本ADRでは「実測して決める」という方針だけを確定し、数値はテスト設計・実装時に埋める。

**実装順序**: #3（dead code除去、無関係だが同ファイルの変更が絡むため先に片付ける）→ #4（アンチエイリアス）→ #5（窓関数）→ #6（docstringで差分を明記）→ #1（#4/#5後の値で閾値を実測して引き直す）。#4/#5/#6/#1 は **1つのPRとしてまとめてマージする**（アトミックに導入する。理由は「影響」を参照）。#3のみ独立したPRで先行させてよい。

**「バグとして直す/近似として残す」の判定基準**: 信号処理として情報が失われる誤り（エイリアシング、スペクトル漏れなど）は直す。パラメータ選択上の近似（K\*固定、矩形帯域分割など）は残し、docstringに明記する。この基準を#6のdocstringにもそのまま書く。

**実測の受け入れ基準**: 閾値の実測は、Issue本文の検証条件（3秒・4Hz変調の合成疑似音声、指数減衰ノイズRIRをRT60=Dry/0.16/0.36/0.61/1.0sの5条件で畳み込み）を最低限の母集団として使う。これは実収録音声ではなく合成音声によるベンチマークであることを明記した上で採用する（実機・実収録での追加検証は将来の改善候補とし、本ADRのスコープには含めない）。この5条件でのSRMR分布を実測し、`_SRMR_TARGETS` をその分布に基づいて設定する。実測条件と結果は#1実装時のPR説明に残す。

## 影響

- SRMR値が実装変更前後で変わる。**#4/#5/#6/#1は1つのPRでアトミックにマージし、「新しいSRMR値」と「新しい閾値」が食い違ったまま存在する過渡区間を作らない**（レビュー指摘: 閾値定数と実装のスケールが不整合な期間があると、その間の`overall`判定が意味を持たなくなり、事後的に無効化できない）。
- `tests/test_srmr.py` に数値アサーションがある場合、#4/#5適用後に見直しが必要。
- 「Reference: Falk et al. (2010)」という表記は、docstringで「原法の簡略実装であり、SRMRpy等の絶対値とは一致しない」と明記する形に変更する（#6）。
- **性能への影響**: `scipy.signal.decimate`はデフォルトでIIRローパス（8次Chebyshev）を追加でかけるため、23チャンネル分の計算コストが増える。#4実装時に、決定前後でチャンク処理のレイテンシを計測し、500msチャンク（#2適用後は3秒窓）の処理がリアルタイム予算内に収まることを確認する。収まらない場合は`decimate`ではなく軽量なFIRアンチエイリアス+ストライドダウンサンプルに切り替える（レビュー指摘への対応）。
- 許容するリスク: K\*固定・矩形帯域分割という近似は残る。将来的にSRMRpyとの相関が実用上問題になった場合は別ADRで完全準拠を再検討する。

## レビュー結果

`性能` `複雑性` `データモデル` の3観点でレビューを実施。

| 指摘 | 重要度 | 対応 |
|---|---|---|
| decimateのIIR追加によるCPU負荷増が影響節に未記載 | Major（性能） | 決定を変更: 影響節に計測方針と代替案を明記 |
| 実測の受け入れ基準（サンプル数・条件）が未定義 | Major（複雑性） | 決定を変更: 実測条件をIssue本文の5条件に固定して明記 |
| 「準拠の範囲」の判断基準が未定義 | Minor（複雑性） | 決定を変更: バグ/近似の判定基準を一文で明記 |
| 閾値定数が旧スケールのまま実装だけ変わる過渡区間で不整合 | Blocker（データモデル） | 決定を変更: #4/#5/#6/#1を1PRでアトミックにマージする方針に変更 |
| 実測の母集団定義（合成/実収録）が曖昧 | Major（データモデル） | 決定を変更: 合成音声ベンチマークであることを明記し、実収録検証は将来課題として切り出す |

Blocker 1件・Major 3件・Minor 1件はすべて決定・影響への反映で解消。未決着の指摘なし。
